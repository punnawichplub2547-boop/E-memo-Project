# Memo Template Search & Scale — Design

**วันที่:** 2026-08-03
**สถานะ:** ทำเสร็จแล้ว (2026-08-04) — ดู `docs/superpowers/plans/2026-08-04-memo-template-search.md`
**โปรเจกต์:** HR&GA E-Memo Sandbox (`D:\Hrproject\sandbox`)

## โจทย์

มี requirement เข้ามาว่าผู้ใช้คนหนึ่งอาจสะสมแม่แบบ (template) เกิน 50 อัน ต้อง (1) รองรับจำนวนที่มากขึ้น และ (2) ค้นหาแม่แบบได้ในหน้า `/create`

**พฤติกรรมผู้ใช้ที่ต้องรองรับเป็นพิเศษ:** ผู้ใช้อาจตั้งชื่อแม่แบบตามเดือนที่ใช้ เช่น `ซื้อยาง EPDM ม.ค.` / `ซื้อยาง EPDM ก.พ.` ⇒ **ชื่อที่คล้ายกันมากคือเรื่องปกติที่ตั้งใจ ไม่ใช่ความผิดพลาด** การออกแบบต้องไม่ขัดขวางพฤติกรรมนี้ และต้องช่วยให้ผู้ใช้แยกแม่แบบที่ชื่อคล้ายกันออกจากกันได้

## สิ่งที่พบจากการสำรวจของเดิม

| ประเด็น | สถานะปัจจุบัน |
|---|---|
| เพดานจำนวน | **ไม่มี** — ตาราง `memo_templates` เก็บได้ไม่จำกัดอยู่แล้ว ปัญหาจริงอยู่ที่ payload กับ UI ไม่ใช่ที่ DB |
| `GET /api/templates` | คืน `template_json` **เต็มทุกอัน** ตั้งแต่เปิดหน้า create |
| ขนาดต่ออัน | ~3–8 KB (มี `requestItems`, `priceComparisons`, `readRecipients` เป็น array) ⇒ **52 อัน ≈ 150–400 KB ต่อการเปิดหน้าหนึ่งครั้ง** ทั้งที่ใช้จริงแค่อันเดียว |
| UI | ชิปเรียงต่อกันแบบ wrap ทั้งหมด ไม่มีค้นหา ไม่มีแบ่งหน้า |
| ความเป็นเจ้าของ | ผูกกับ `user_id` = ส่วนตัวรายบุคคล ไม่มีการแชร์ |

**ขอบเขตที่ยืนยันกับผู้ใช้:** แม่แบบยังเป็นของส่วนตัวเหมือนเดิม ไม่ทำแม่แบบกลางขององค์กรในรอบนี้

## แนวทางที่เลือก

**ทาง A — API ส่งรายชื่อเบา + ค้นฝั่ง browser**

ทางเลือกที่พิจารณาแล้วไม่เอา:
- **ค้นฝั่ง server + แบ่งหน้า** — รองรับได้ไม่จำกัดจริง แต่ซับซ้อนกว่ามาก (debounce, race condition, collation ภาษาไทย) และทุกครั้งที่พิมพ์ต้องรอ network ซึ่งแย่กว่าที่จำนวน 52 รายการ · เก็บไว้ทำเมื่อตัวเลขจริงแตะหลักพัน
- **เพิ่มแค่ช่องค้นหาใน UI ไม่แตะ API** — งานน้อยสุดแต่ไม่แก้ปัญหา payload ที่ทำให้หน้า create อืดตอนเปิด

## สถาปัตยกรรม

### ชั้น DB — `src/lib/db-templates.ts` (ไม่แตะ schema)

แยก type สองระดับ ให้ TypeScript บังคับเองว่าที่ไหนได้ข้อมูลเบา ที่ไหนได้เต็ม:

```ts
export interface MemoTemplateSummary {
  id: number;
  name: string;
  category: string | null;   // ดึงจาก template_json
  updatedAt: string;
}
// MemoTemplate เดิม (มี templateJson) ใช้เฉพาะตอนโหลดจริง
```

`getTemplatesByUserId()` เปลี่ยน SQL เป็น:

```sql
SELECT id, name,
       JSON_UNQUOTE(JSON_EXTRACT(template_json, '$.category')) AS category,
       updated_at AS updatedAt
FROM memo_templates
WHERE user_id = ?
ORDER BY updated_at DESC
```

`JSON_EXTRACT` ทำงานฝั่ง MySQL ⇒ ไม่ต้องส่ง JSON ก้อนใหญ่ข้ามเน็ต และไม่ต้องมี migration

**เรียงด้วย `updated_at DESC`** (เดิม `id DESC`) เพราะเมื่อมีแม่แบบรายเดือนจำนวนมาก อันที่เพิ่งใช้หรือเพิ่งแก้มีโอกาสถูกใช้ซ้ำมากกว่าอันที่เพิ่งสร้าง

### ชั้น API

| Route | เดิม | ใหม่ |
|---|---|---|
| `GET /api/templates` | คืน `template_json` เต็มทุกอัน | คืน `MemoTemplateSummary[]` (~3 KB ที่ 52 อัน) |
| `GET /api/templates/[id]` | **ยังไม่มี** | **เพิ่มใหม่** — คืน JSON เต็มอันเดียว, เช็ค `user_id === session.userId` |
| `POST` / `PUT` / `DELETE /api/templates/[id]` | — | ไม่เปลี่ยน |

`GET /api/templates/[id]` คืน **404 เมื่อไม่ใช่เจ้าของ** (ไม่ใช่ 403) เพื่อไม่บอกใบ้ว่า id นั้นมีอยู่จริง — ตรงกับที่ `PUT`/`DELETE` ใน `src/app/api/templates/[id]/route.ts` ใช้อยู่แล้ว (`"Template not found or not owned by user"`, 404)

**รูปแบบวันที่:** API ส่ง `updatedAt` เป็นค่าดิบจาก MySQL (`DATETIME`) ตามที่ `db-templates.ts` ทำอยู่เดิม · การจัดรูปแบบให้อ่านง่าย (`28 ก.ค.`) เป็นหน้าที่ของ UI ฝั่ง client เท่านั้น

### ชั้น hook — `src/app/create/_hooks/useMemoTemplates.ts`

`handleLoadTemplate` เปลี่ยนจาก sync เป็น async: เดิมรับ `data` ที่ parse มาแล้วจากลิสต์ ใหม่จะ fetch JSON เต็มเองตอนผู้ใช้คลิก แล้วจึงเรียก `applyBulkData` · มี state บอกว่ากำลังโหลดแม่แบบ id ไหนอยู่ เพื่อให้ UI แสดงสถานะเฉพาะชิปนั้น

### ชั้น UI — `src/app/create/_components/TemplateSelectorCard.tsx`

```
┌─ ⚡ โหลดจากแม่แบบคำขออนุมัติ (52) ─────────────────────┐
│  🔍 ค้นหาแม่แบบ...                                    │
│  [ทั้งหมด 52] [วัตถุดิบ 18] [บริการ 12] [ทั่วไป 10]…  │
│                                                        │
│  ┌────────────────────────┐ ┌──────────────────────┐ │
│  │ ซื้อยาง EPDM ก.ค.    ✕ │ │ ซื้อยาง EPDM มิ.ย. ✕ │ │
│  │ วัตถุดิบ · 28 ก.ค.     │ │ วัตถุดิบ · 30 มิ.ย.  │ │
│  └────────────────────────┘ └──────────────────────┘ │
│                    ⌄ แสดงเพิ่ม (อีก 44)               │
└────────────────────────────────────────────────────────┘
```

- **ชิปสองบรรทัด** — ชื่อ + `หมวดหมู่ · วันที่อัปเดต` เพราะแม่แบบรายเดือนมีชื่อคล้ายกันจนแยกด้วยชื่ออย่างเดียวไม่ได้ วันที่คือตัวแยกจริง
- **ค้นแบบ substring ไม่สนตัวพิมพ์เล็กใหญ่ ค้นทั้งชื่อและหมวดหมู่พร้อมกัน** — พิมพ์ `EPDM` ได้ครบทุกเดือน, พิมพ์ `วัตถุดิบ` ได้ทั้งหมวด
- **แสดง 12 อันแรก + ปุ่มแสดงเพิ่ม** — เมื่อค้นแล้วเหลือน้อยกว่า 12 แสดงหมดทันทีโดยไม่ต้องกด
- **ปุ่มกรองหมวดมีตัวเลขกำกับ** และซ่อนหมวดที่มี 0 อัตโนมัติ
- **ปุ่มลบยัง confirm เหมือนเดิม** แต่ข้อความ confirm มีวันที่กำกับ (`ลบ "ซื้อยาง EPDM ก.ค." (28 ก.ค.)?`) กันลบผิดตัวเมื่อชื่อคล้ายกัน
- แยก logic กรอง/ค้นออกเป็น `src/lib/template-filters.ts` แบบ pure function เพื่อทดสอบได้โดยไม่ต้อง render

### ชื่อซ้ำ

**ไม่บล็อกและไม่เตือนล่วงหน้า** เพราะผู้ใช้ตั้งชื่อคล้ายกันโดยตั้งใจ · เฉพาะกรณีพิมพ์ชื่อ**ตรงกันเป๊ะ**กับแม่แบบที่มีอยู่ ให้ modal บันทึกเสนอปุ่ม "ทับอันเดิม" ให้กดง่าย (ใช้กลไก `overwriteId` ที่มีอยู่แล้ว) — ไม่กดก็บันทึกเป็นอันใหม่ตามปกติ

"ตรงกันเป๊ะ" นิยามว่า: เทียบหลังตัดช่องว่างหัวท้ายแล้ว **ไม่สนตัวพิมพ์เล็กใหญ่** (เกณฑ์เดียวกับการค้นหา) · การตรวจนี้ทำฝั่ง client จากรายชื่อที่โหลดมาแล้ว ไม่ต้องยิง API เพิ่ม

## กรณีที่ต้องรับมือ

| สถานการณ์ | พฤติกรรม |
|---|---|
| template เก่าที่ไม่มี `category` | `JSON_EXTRACT` คืน `NULL` → จัดกลุ่ม `ไม่ระบุหมวด` และยังค้นด้วยชื่อได้ปกติ **ของเดิมทุกอันต้องใช้ต่อได้โดยไม่ต้องแก้อะไร** |
| คลิกโหลดแต่แม่แบบถูกลบไปแล้ว (เปิดสองแท็บ) | 404 → toast `แม่แบบนี้ถูกลบไปแล้ว` + รีเฟรชรายการ **ไม่ทับฟอร์มที่กรอกไว้** |
| โหลดล้มเหลว (network / 500) | toast แจ้ง + ฟอร์มคงเดิมทุกช่อง ห้าม apply ข้อมูลบางส่วน |
| JSON เสีย | toast แจ้ง + log ไม่ให้หน้าขาว |
| ยังไม่มีแม่แบบเลย | ข้อความแนะนำเดิม ไม่แสดงช่องค้นหา/ตัวกรองให้รก |
| มีแม่แบบแต่ค้นไม่เจอ | `ไม่พบแม่แบบที่ตรงกับ "…"` + ปุ่มล้างคำค้น |
| โหมดแก้ไข-ส่งใหม่ (revision) | ไม่แสดงการ์ดนี้เลย เหมือนเดิม |

## Deploy

**ไม่มี migration** — ไม่แตะ schema เลย ⇒ prod แค่ pull + rebuild ตามปกติ ไม่ต้องระวังกับดัก migration map (ERR-0026) ในรอบนี้

## สิ่งที่ไม่ทำในรอบนี้ (YAGNI)

- แม่แบบกลางขององค์กร / การแชร์แม่แบบข้ามผู้ใช้
- ค้นเนื้อหาข้างในแม่แบบ (ชื่อ vendor, รายการของ) — ตกลงว่าค้นแค่ชื่อ + หมวดหมู่
- แบ่งหน้าฝั่ง server, การจัดกลุ่มแบบโฟลเดอร์, ติดดาว/ปักหมุด
- จำกัดจำนวนแม่แบบต่อผู้ใช้
